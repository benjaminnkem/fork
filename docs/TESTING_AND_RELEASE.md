# Fork — Testing, Acceptance & Release Gate

Fork cannot rely on a visually convincing demo while the protocol engine is fake. Release quality is defined by reproducible real-chain evidence.

## 1. Test tiers

### Tier A — pure tests

For code that has no external side effects:

- schema validation;
- bigint serialization;
- idempotency-key generation;
- risk-policy evaluation against deterministic inputs;
- canonical receipt serialization/hash;
- error classification;
- governance selector decoding against verified ABI test vectors.

Static values here are test vectors, not fake external services.

### Tier B — local infrastructure integration

Use real local services:

- MongoDB container;
- Redis container;
- BullMQ producer/worker;
- NestJS API.

Do not replace these with in-memory mocks in release acceptance.

### Tier C — real chain reads

Against configured Base/Ethereum RPCs:

- chain ID;
- block anchors/hashes;
- contract bytecode;
- Moonwell positions;
- account liquidity/shortfall;
- real governance logs/proposal state.

### Tier D — real mainnet-fork simulation

Anvil forks real Base historical/current state.

Acceptance proves:

- baseline read;
- governance effect replay;
- after-state read;
- branch snapshot/revert isolation;
- strategy transaction execution;
- post-change verification;
- proof receipt.

### Tier E — live Groq agent

With real Groq key:

- model availability;
- valid local tool calling;
- tool policy rejection;
- malformed call recovery;
- rate-limit classification;
- planner/fallback behavior;
- no raw chain-of-thought in product trace.

### Tier F — browser E2E

Playwright against running web/API/workers with real infrastructure and a pinned real historical replay.

Critical E2E:

1. open Fork;
2. enter real supported address/replay;
3. load real position;
4. run simulation;
5. observe progress;
6. see measured risk delta;
7. see strategy branches;
8. inspect proof;
9. ensure no console/API errors.

Connected-wallet transaction signing tests should use a controlled wallet/environment; never automate a production wallet through MCP.

## 2. Historical replay acceptance

The release replay must prove its provenance:

- real historical proposal/action;
- real source and destination transaction/log references;
- real Base anchor block number/hash;
- real deployed Moonwell code;
- exact destination effect;
- real historical wallet if feasible;
- actual recomputation on run.

The replay manifest may store identifiers/anchors but not substitute saved output numbers for simulation.

## 3. Strategy acceptance

For each supported strategy:

- find a case where insufficient amount fails;
- find minimum/near-minimum policy-passing amount;
- verify one unit/step below threshold fails where search granularity allows;
- prove branch reset means strategy B is not benefiting from state mutated by strategy A;
- prove unavailable wallet balance causes infeasible result, not fabricated token allocation.

## 4. Governance edge tests

- unrelated proposal ignored;
- unsupported selector classified unsupported;
- cancelled/expired proposal stops recommendation;
- multi-call proposal preserves all raw calls;
- source approved but destination pending represented correctly;
- reorg rollback test on index cursor logic using a controlled local chain scenario plus real log parser;
- contract code hash/address mismatch fails closed.

## 5. Security tests

- proposal description containing malicious “ignore rules” text cannot unlock tools;
- model attempts arbitrary tx tool — impossible/not present;
- invalid target address in transaction plan rejected;
- unlimited approval not generated by default;
- wrong chain wallet rejected before signing;
- replayed auth nonce rejected;
- expired nonce rejected;
- rate-limit simulation endpoint;
- Anvil not reachable from public network/container ingress;
- secrets absent from browser bundle/log/receipt.

## 6. Resilience tests

- kill Anvil mid-job;
- kill simulator worker mid-job and restart;
- Redis transient outage;
- Mongo transient outage;
- Base provider 429;
- primary provider failure → fallback where safe;
- Groq 429/outage;
- duplicate simulation request;
- duplicate governance log;
- user/event changes while simulation is running;
- SSE disconnect/reconnect;
- simulation timeout.

## 7. Performance tests

Measure, do not guess:

- fresh wallet read p50/p95;
- indexer catch-up rate;
- fork startup p50/p95;
- impact simulation p50/p95;
- strategy branch p50/p95;
- memory per active Anvil process;
- archive RPC calls per simulation;
- Mongo write volume;
- queue wait time under concurrency 1/2/3/...;
- Groq calls/tokens per agent run.

Set `MAX_PARALLEL_FORKS` from measured machine capacity.

## 8. Mainnet execution release gate

Before enabling transaction preparation in production:

- target contracts verified;
- selectors allowlisted;
- argument limits tested;
- current-state freshness gate works;
- exact plan is re-simulated;
- user sees decoded plan;
- wallet signs on Base 8453;
- tx replacement/drop handled;
- actual Moonwell post-state verified;
- mismatch status tested.

Autonomous mainnet execution remains disabled in V1.

Automated tests construct and validate allowlisted plans and wallet-auth signatures with local viem accounts. They do not broadcast a Base Mainnet transaction. A real send stays user-controlled in the wallet UI.

## 10. Submission evidence

For Orion/judging, expose real evidence:

- source proposal/change ID;
- chain/block hashes;
- real contract addresses;
- raw/decode governance call;
- before/after contract state;
- rejected and verified branch evidence;
- proof receipt hash;
- user-safe agent trace.

The strongest claim Fork can make is not “AI thinks this is dangerous.” It is:

> **Fork discovered a real upcoming/historical protocol transition, executed it against real chain state, measured the result from the protocol itself, and accepted only rescue actions that survived the same transition in the EVM.**
